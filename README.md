# Andromeda backend schema v1

В репозитории подготовлены SQLAlchemy 2 ORM-модели и Alembic-миграция начальной PostgreSQL-схемы из ERD Schema v1. Так как папка проекта была пустой, используется синхронный SQLAlchemy с драйвером psycopg 3; дополнительный web/API слой не создавался.

## Запуск миграций

Нужны Python 3.11+ и PostgreSQL 13+ (`gen_random_uuid()` встроен в PostgreSQL 13 и новее).

```powershell
python -m pip install -e .
$env:DATABASE_URL = "postgresql+psycopg://USER:PASSWORD@HOST:5432/DATABASE"
alembic upgrade head
```

`DATABASE_URL` задаётся отдельно для приложения и Alembic. Файл `.env.example` содержит шаблон, но сам по себе не загружается автоматически. Для приложения можно создать engine через `andromeda.db.session.create_db_engine()`.

Откат начальной версии:

```powershell
alembic downgrade base
```

## Структура

40 ORM-таблиц сгруппированы по предметным областям:

- приём: университеты, программы, кампании, offering, конкурсные пулы, статистика, экзаменационные требования, олимпиады;
- учебные планы: curricula, курсы и предметные области;
- правила: правила, неизменяемые опубликованные версии, наборы правил и их участники;
- пользовательские профили, результаты экзаменов и олимпиад, shortlist;
- provenance: источники и полученные артефакты;
- ontology: типы объектов, свойств и связей, ссылки на объекты и assertions.

Основные модели находятся в `src/andromeda/db/models/`, общая `Base` и naming convention — в `src/andromeda/db/base.py`, engine factory — в `src/andromeda/db/session.py`. Начальная миграция находится в `alembic/versions/`.

UUID генерируется PostgreSQL через `gen_random_uuid()`; `uuid4` на стороне ORM оставлен для генерации идентификатора до INSERT. Все денежные суммы, оценки и кредиты хранятся в `NUMERIC`; даты календаря — `DATE`; временные отметки и valid-time provenance — `TIMESTAMPTZ`. Assertions хранят текстовое `value`, как указано в ERD; `data_type='json'` означает JSON-сериализованное значение, отдельной JSON-колонки в ERD нет. Поэтому JSONB и GIN-индексы не добавлялись.

## Целостность данных

- Коды университетов, экзаменов, правил и справочников уникальны; локальные коды программ и кафедр уникальны в университете. Кампания уникальна по университету и году; offering — по программе, кампании, форме обучения и языку; пул — по offering, типу финансирования и квоте; статистика — по пулу и году.
- `program_offering` хранит `university_id` дополнительно к ERD и ссылается составными FK одновременно на программу и кампанию. `program_department` использует тот же приём. PostgreSQL не примет связи через границу университетов.
- Типы ontology продублированы в дочерних строках и закреплены составными FK: fact связывает объект только со свойством его типа; link assertion — только с объектами объявленных source/target типов. Trigger также проверяет, что текстовое значение fact разбирается в заданный `data_type`.
- `cardinality` у link type ограничен известными значениями, но не ограничивает набор raw assertions: независимые источники и исторические интервалы могут содержать противоречивые связи. Кардинальность следует применять при последующей сборке canonical view/proposal.
- Условия экзаменов имеют типизированные exam/operator узлы, FK родителя внутри того же requirement set и не более одного корня. CHECK-ограничения взаимоисключают exam и operator поля и проверяют `min_count`; отложенный constraint trigger запрещает циклы, оператор без нужного числа детей и exam-узел с детьми. Поддерживаются `and`, `or` и `at_least`.
- Наборы правил содержат конкретные опубликованные версии, по одной версии каждого правила. Создавать их можно только как draft; перед публикацией набор должен содержать хотя бы одну опубликованную версию. После публикации правило, версия, набор и состав набора неизменяемы на уровне БД.
- `valid_to` может быть пустым для открытого интервала; CHECK требует `valid_to > valid_from`, если конец задан. Assertions остаются provenance-записями и не подменяют canonical domain tables. Recorded-time поле намеренно не добавлялось.
- Изменяемые значения финансирования, квот, типов правил, льгот, результатов олимпиад и типов источников представлены lookup-таблицами. Их значения не зашиты миграцией: перечни должны быть заполнены подтверждёнными кодами из источников Andromeda. Закрытые технические множества (типы requirement node/operator, статусы публикации, ontology data types и cardinality) ограничены CHECK.
- FK исторических и канонических данных используют `RESTRICT`; каскад оставлен для чистой связи программа–кафедра и пользовательского shortlist. Для каждого FK создан подходящий дочерний индекс; временные индексы добавлены для provenance-запросов, широкие JSON-индексы не создавались.

Триггеры в миграции: `trg_requirement_node_tree_valid`, `trg_fact_assertion_value_type`, `trg_policy_rule_version_immutable`, `trg_policy_rule_immutable_after_publish`, `trg_rule_set_immutable_after_publish`, `trg_rule_set_member_immutable_after_publish`.

## Проверка

Начальная миграция была запущена на отдельной чистой PostgreSQL 17.11 базе. `alembic upgrade head`, `alembic check`, `alembic downgrade base` и повторный `alembic upgrade head` завершились успешно. Дополнительно проверены негативные вставки для межуниверситетского offering, дубля конкурсного пула, неверных requirement/ontology типов, типа значения fact, цикла дерева требований и изменения опубликованных правил/набора; PostgreSQL отклонил их соответствующими FK, UNIQUE, CHECK и trigger-ограничениями. После downgrade таблицы и функции миграции удалились; осталась только созданная Alembic системная таблица до следующего upgrade.
